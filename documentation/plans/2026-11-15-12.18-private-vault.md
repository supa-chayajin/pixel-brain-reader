# 12.18 — Private vault hardening (plan, 2026-11-15)

The roadmap's 12.18 items (`2026-11-10-dream-app-roadmap.md`): **V1** change the password, **V2**
auto-lock, **V3** the fingerprint-bound password, and **D5a**, the two Tech watch follow-ups. The
owner reviewed it in an interview on 2026-11-15, right after the 12.17 release.

## Decisions (owner, 2026-11-15)

- **D1 History.** A new password re-encrypts every note, but git history keeps each older version
  under the old password. History stays as it is, and the change screen says so in one line. It is
  a safety net if the new password is forgotten, and a risk only if the old one leaked to someone
  who also has a copy of the vault.
- **D2 Auto-lock.** The journal locks 5 minutes after it leaves the screen (another app, Home, the
  screen turning off). Its menu changes the delay: at once, 1, 5 or 15 minutes. Locking also ends
  private notes in Chat answers.
- **D3 V3 now.** The password sits behind a Keystore key that only a strong biometric opens. Nothing
  in the background can read it any more.
- **D4 New passwords.** At least 12 characters, no other rule.
- **D5 Unlock order.** Face (when the phone rates it strong), then fingerprint, then the journal's
  password. Never the phone's PIN.
- **D6 Timing.** Built the same night; the fingerprint checks are the owner's, on a device.

## What the design rests on (checked 2026-11-15)

- **Format.** A `.md.enc` file is salt (16) + IV (12) + AES-GCM. The key comes from PBKDF2-SHA256 at
  210k rounds, with 10k tried for older notes. New encryptions share one salt per password per
  process.
- **The password today.** It is kept in the encrypted preferences, which the app reads without
  the owner. The biometric prompt only guards the screen; on success it reads that copy. It is used
  by:
  - the journal;
  - private retrieval in Chat, only while the journal's session flag is on;
  - the indexer, when "Private notes in AI answers" is on;
  - an encrypted mission log, also from the background: Focus's "Log it", the shutdown win and the
    23:50 monthly report.
- **The AI index** keeps private passages encrypted with the same password (Room,
  `PrivatePassageCodec`).
- **"Unlocked"** is a process-wide flag set by the journal's ViewModel. It lasts until that
  ViewModel is cleared, so a journal left in Recents stays unlocked.
- **The encrypted files** are every `*.md.enc` in the vault: the journal (`99_Private/`), and an
  encrypted log's months, ADRs and reports (`99_Private/Mission log/`). Only this phone writes them:
  the tablet is read-only and the desktops never decrypt. The vault has no `mission_log.json`, so
  the owner's log is the plain one.
- **Android.** A key bound to biometrics opens only with a Class 3 (strong) biometric. The tablet's
  only sensor is a strong fingerprint (`dumpsys biometric`: modality 2, strength 15). Google says
  Face Unlock on the Pixel 8 and later, Folds included, can sign into apps, which means strong. The
  Fold itself is checked on the device.

## Design

### The session (V2 and V3)

`data/privatevault/PrivateVaultSession` is the process's one session:

- **The password.** Held as a `CharArray` from an unlock until a lock wipes it, along with the
  derived keys. `withPassword {}` hands out a copy for one operation. Encrypted writes run under the
  session's write lock, which the password change holds while it runs.
- **Auto-lock.** A screen that shows private content holds the session (the journal while it is on
  screen). When nothing holds it, a deadline runs (`elapsedRealtime` + the delay). It is checked on
  every read, so it survives sleep and a frozen process, and a timer flips it too.
  - A session opened without the journal starts its deadline at once.
  - Closing the journal (Back) locks at once, as today.
  - The delay lives in `UserPreferencesRepository` (device-only, 5 minutes by default).
- **What it replaces.** `SecretManager`'s session flag and every `getVaultPassword()` read.

### V3: the password behind a strong biometric

`data/privatevault/VaultPasswordBinding`:

- **The key.** An RSA-2048 Keystore key. Decrypting needs `AUTH_BIOMETRIC_STRONG` at each use, and a
  new enrolment invalidates it.
- **The wrapped password.** The password is wrapped with the public key, which needs no prompt, so a
  password change re-binds without one. It is kept in the encrypted preferences, and only
  BiometricPrompt with a `CryptoObject` unwraps it.
- **The prompt.** `BIOMETRIC_STRONG`, no device credential, "Use password" as the other button, no
  confirm tap. The system tries the face first when it is strong, and the fingerprint otherwise
  (D5).
- **Failures.** A new face or fingerprint invalidates the key: the wrapped copy is dropped, the
  password is typed once, and it is bound again. Without a strong biometric, the password is typed
  every time.
- **Migration.** At start, the readable copy is wrapped. It is deleted at the first unlock that
  proves the new path works (the face or fingerprint, or the typed password), so a forgotten
  password with a working fingerprint never locks anyone out. Nothing else reads it from 12.18 on.
- **What stops running in the background:**
  - **Private notes in AI** (when on): embedded only while the session is open, with indexing
    requested at unlock. A locked session skips private notes and never purges their vectors; only
    the switch purges, as today.
  - **Private retrieval** reads the session. Its meaning is unchanged.
  - **An encrypted mission log** works while the session is open; otherwise it shows the existing
    "unlock" error. Focus's "Log it" isn't offered for an encrypted log, because a notification can't
    ask for a fingerprint. Its monthly work report is retried each night and written at the next
    unlock. A plain log, like the owner's, doesn't change.

### V1: change the password, crash-safe

- **Where.** The journal's menu → Change password: the current password (typed), then the new one
  twice (12+ characters, D4, and different from the current one). The screen carries D1's line.
- **Who runs it.** `data/privatevault/PrivateVaultRekey`, under the git lock
  (`GitSyncCoordinator.mutex`) and the session's write lock, with the indexer stopped:
  1. **Check.** Every `*.md.enc` must decrypt with the current password. If one doesn't, nothing is
     written and the screen lists it.
  2. **Stage.** Each note is re-encrypted with the new password into `filesDir/private_rekey/`
     (outside the vault), fsynced, then decrypted again and compared. A manifest records each path
     and the SHA-256 of the ciphertext it replaces.
  3. **Swap.** The manifest is marked SWAPPING, then each staged file is renamed over its vault file,
     one atomic rename each. A file that changed since staging stops the swap before the first
     rename.
  4. **After.** The session and the binding take the new password; Room's private passages are
     re-encrypted in one transaction; the manifest and the staged files are deleted; a push is
     requested.
- **A crash.** If it dies while STAGING, the next start rolls it back and the vault is untouched.
  If it dies while SWAPPING, the next start finishes the renames, which need no password.
  `JGitProvider` refuses to commit while a swap is pending, so a half-swapped vault never reaches
  GitHub. Until the swap ends, either password opens the journal: the unlock accepts a password
  that opens any of its sampled notes.
- **Read-only.** Never on a read-only device.
- **The test the gates ask for.** It kills the change at every step (after k files staged, after k
  renamed), then resumes from scratch. Every file must open with the new password, with identical
  text, and a crash while staging must leave the vault as it was.

### D5a: Tech watch

- **New feeds.** A feed with no cached headline, whether a sync added it or the feeds page did, is
  read at once instead of waiting out the 2-hour freshness. The block also re-reads when a sync
  ends (`SyncState.Success`), besides on a return to the app and a mode change.
- **Failing feeds.** The feeds page shows each feed's last read and last failure: a blocked
  address, an HTTP status, not a feed, or no answer. These are kept on the device (DataStore). A
  Check now button reads them all again.

## Not in 12.18

- Raising PBKDF2 above 210k rounds: the 12-character rule protects far more.
- Rewriting the vault's history (D1).
- The phone's PIN as an unlock (D5).
- A fingerprint prompt outside the journal: an encrypted log asks for an unlock of the journal.

## Checks

- **JVM:**
  - the session's deadline (driven by a clock);
  - the binding and the migration, with the Keystore faked;
  - the password change killed mid-way;
  - the indexer: a locked session skips private notes without purging them;
  - the Tech watch's choice of feeds to read.
- **Emulator** (sandbox vault): a test journal under a test password, a password change, the
  auto-lock, and the emulator's fingerprint (`adb emu finger touch`).
- **Owner:**
  - on the Fold: face, then fingerprint, then password; `dumpsys biometric` for the face's class;
    a password change;
  - on the tablet (read-only): it asks for the new password once.
