# 12.15.0 — Sync safety (S1, S2)

**Status:** reviewed by the owner in an interview on 2026-11-11 (gate 1: S1 changes how a sync
conflict is resolved). The six decisions are recorded at the end. The checklist is
`2026-11-10-dream-app-roadmap.md` §3.

## Today

When a pull's rebase conflicts, `JGitProvider.pull` aborts it, `ConflictResolver` copies the
phone's version of each conflicted file to `<name>_sync_conflict_<yyyyMMdd_HHmmss>.<ext>` beside
it, and the sync stops on an error. The phone's commits stay unpushed. Every later sync commits
those backups (the pre-pull commit), hits the same conflict, and writes another backup: the phone
is stuck until something outside the app resolves it. The owner's vault has never had one.

## S1 — Conflict screen

- **The conflict is remembered** on the phone: the conflicted paths, GitHub's commit they conflict
  with, and the backups made for them.
- **Until it is resolved** the pull is paused: pull to refresh says "Resolve the conflict first"
  and opens the screen, and no new backup is written per try. Local saves keep committing on the
  phone (GitHub refuses their push until then, as today) and fold into the resolution.
- **The screen** (route `sync_conflicts`, from a Daily banner "Sync stopped: N files changed on
  both sides", the sync error and Settings) lists each conflicted file with a side-by-side diff of
  the phone's version and GitHub's (the Time Machine's `LineDiff`):
  - **a note or any text file:** keep mine, keep theirs, edit, keep both. Edit opens the editor on
    git's merge, each disagreement marked with the phone's lines then GitHub's. Keep both leaves
    GitHub's version in place and saves the phone's beside it as `<name> (téléphone).md`.
  - **a data file (JSON):** keep mine or keep theirs only, with a short summary of what differs
    (entries only on the phone, only on GitHub, changed) instead of raw JSON.
- **Resolving** runs once every file has a choice, as one operation under the git lock: fetch;
  fold the phone's unpushed commits into one commit; replay it onto GitHub's (a rebase: no merge
  commit, like every sync); at the stop, apply each file's choice; the backups made for this
  conflict are deleted in the same commit; push. If GitHub moved again and a file conflicts
  without a choice, the operation is aborted and the screen shows the new state. Then the pause
  ends and syncing is as before.
- **Read-only device:** it only fast-forwards and never conflicts; no screen there.

## S2 — Read-only polish

The Settings pages and tools that change vault files stay readable on a read-only device; their
controls are disabled with one line, "Change this on your phone", as the feeds and mood-tag pages
already do. The list is inventoried while building: every screen whose action writes the vault.

## Tests first (gate 2)

- Real JGit temp repos (a phone clone and a desktop clone of one bare remote): the conflict
  remembered and the pull paused; each choice (mine, theirs, edited, both) landing as one commit
  on top of GitHub's, the other files' changes merged by git, the backups gone; GitHub moving
  again during the choice aborting cleanly; the push; the paused state cleared.
- The marked merge text, the copy's name, the JSON summary.
- S2: each listed screen's controls disabled on a read-only device.

## Decisions (owner, 2026-11-11, interview)

1. **How a resolution lands:** one commit on top of GitHub's, no merge commit.
2. **Edit starts from** git's merge, both sides marked.
3. **Keep both:** GitHub's version in place, the phone's as a copy `<name> (téléphone).md`.
4. **Until resolved:** the pull pauses; local saves keep working.
5. **Data files (JSON):** keep mine or keep theirs, with a summary of what differs.
6. **S2:** pages readable, controls disabled, "Change this on your phone".
